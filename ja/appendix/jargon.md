# 付録 B　現場の言い回し

ソフトウェアのチームでは、日本語に英語の用語を混ぜた会話がふつうです。たとえば「PR 出す前に rebase しといて」。チームに入ったばかりの人が初めて聞くと、何のことかわからないことがよくあります。

この付録では、チームでよく耳にする言い回しを例文付きで集めました。言い方はチームによって少しずつ違いますが、ここでは一般的なものを取り上げています。正式な定義は[付録 A　用語集](glossary.md)を参照してください。

---

## 日々のコミット

| 言い回し | 意味 | 例文 |
|---|---|---|
| コミットしとく | いまの変更を 1 つのバージョンとして記録する | 「区切りがついたらコミットしといて。1 日中ためないで」 |
| ステージする | 変更をステージングエリアに入れる。つまり `git add` | 「バグ修正のファイルだけステージして。デバッグ出力は入れないで」 |
| 作業ツリーが汚れてる | コミットしていない変更がある（dirty） | 「作業ツリーが汚れてるから、コミットか stash してからブランチを切り替えて」 |
| きれい | コミットしていない変更が 1 つもない（clean） | 「`git status` がきれいになったから切り替えられるよ」 |
| コミットハッシュ | コミットの番号。普通は先頭 7 文字だけ言う | 「バグ報告にはコミットハッシュを付けて。先頭 7 文字で十分」 |
| メッセージをちゃんと書く | コミットメッセージに何をなぜ変えたかを書く | 「`fix` だけじゃわからないよ。メッセージをちゃんと書いて」 |

## ブランチとマージ

| 言い回し | 意味 | 例文 |
|---|---|---|
| ブランチを切る | いまのコミットから新しいブランチを作る | 「この機能はブランチを切ってやって。main を直接いじらないで」 |
| 切り替える | 別のブランチに移る | 「main に切り替えて、最新を pull してからブランチを切って」 |
| マージして戻す | ブランチを `main` にマージする | 「テストが終わったら main にマージして」 |
| main を取り込む | `main` の新しいコミットを自分のブランチにマージし、追いつく | 「ブランチがだいぶ遅れてるから、先に main を取り込んで」 |
| rebase しとく | 自分のコミットを最新の `main` の後ろに付け直す | 「PR 出す前に rebase しとくと、履歴がきれいになるよ」 |
| コンフリクトを解消する | マージのときのコンフリクトを処理する | 「この 2 つの PR は同じファイルを触ってるから、後からマージする人がコンフリクトを解消して」 |
| 早送りで進む | マージがブランチを前に進めるだけで済む（fast-forward） | 「main に新しいものはないから、早送りで進むだけだよ」 |
| 長生きブランチ | 長い間マージされないまま残っているブランチ | 「長生きブランチは最後のマージが大変だから、1、2 日でマージしよう」 |

## リモート

| 言い回し | 意味 | 例文 |
|---|---|---|
| プッシュする、上げる | `git push` | 「直したら上げといて。見ておくから」 |
| プルする、落とす | `git pull` | 「朝いちばんに pull してから書き始めて」 |
| fetch してみる | マージせずにダウンロードだけして、リモートの様子を見る | 「fetch して、origin を誰か触ってないか見てみて」 |
| 遅れてる、進んでる | 手元のブランチがリモートより少ない、または多い（behind、ahead） | 「君の main は origin より 3 コミット遅れてるよ」 |
| 強制プッシュ、force push | `git push --force` でリモートの履歴を上書きする | 「共有済みのブランチには、絶対に force push しないで」 |
| リポを作る | GitHub に新しいリポジトリを作る | 「このツールは別にリポを作って置こう」 |

## プルリクエストとレビュー

| 言い回し | 意味 | 例文 |
|---|---|---|
| PR を出す、PR を立てる | プルリクエストを作る | 「直したら PR を出して、レビュアーに私を指定して」 |
| レビューする | ほかの人の変更を確認する | 「この PR、誰かレビューできる人いる？」 |
| Approve する | レビューを通す | 「マージには 2 人の Approve が必要だよ」 |
| LGTM | Looks Good To Me。問題なさそう | 「LGTM、マージしていいよ」 |
| nit | 細かい指摘で、直さなくてもかまわない | 「nit：この変数名、もう少しわかりやすくできそう」 |
| Request changes をもらう | レビューで、直してからマージするよう求められる | 「PR に Request changes をもらったから、直してもう一度プッシュする」 |
| CI が落ちた、CI が赤い | 自動チェックが通らなかった | 「CI が落ちてる。まずどのテストが通らなかったか見て」 |
| squash する | 複数のコミットを 1 つにまとめる | 「細かいコミットは squash してからマージして」 |
| ドラフト PR | 未完成だが、方向性を見せるために先に出す PR | 「やり方を相談したいから、先にドラフト PR を出しておいて」 |
| PR をマージする | マージボタンを押す | 「CI も通ったし Approve ももらえたから、PR をマージするね」 |

## リリース

| 言い回し | 意味 | 例文 |
|---|---|---|
| タグを打つ | あるコミットにバージョンのタグを付ける | 「v1.0.0 のタグは打った？」 |
| リリースする | 正式にバージョンを公開する | 「金曜にリリースするから、木曜以降は修正だけね」 |
| hotfix | リリース済みのバージョンの緊急修正 | 「出荷したバージョンに問題が出た。v1.0.0 から hotfix ブランチを切って直そう」 |
| コードフリーズ | リリース前に新機能の追加を止める | 「来週からコードフリーズだから、新機能は次のバージョンで」 |
| バージョンを上げる | セマンティックバージョニングに従って番号を上げる | 「設定の形式を変えて互換性がなくなったから、メジャーバージョンを上げよう」 |

## 困ったとき

| 言い回し | 意味 | 例文 |
|---|---|---|
| revert する | `git revert` でコミットを取り消す | 「もうプッシュしたなら、reset じゃなくて revert して」 |
| reset で戻す | `git reset` でブランチを過去に戻す | 「まだプッシュしてないなら、1 つ前のコミットに reset で戻せばいいよ」 |
| stash しとく | コミットしていない変更をいったんしまう | 「書きかけは stash しといて、バグ修正の方に切り替えて」 |
| reflog を見る | `git reflog` で「消えた」コミットを探す | 「コミットが消えた？ 慌てないで、reflog を見てみて」 |
| blame してみる | `git blame` で、ある行をどのコミットが変えたかを調べる | 「この行、blame してみて、なぜ変えたのか確かめよう」 |
| パスワードをコミットしちゃった | 秘密情報が履歴に入ってしまった | 「パスワードをコミットしちゃった。まずパスワードを変えて、履歴はそれから」 |

「blame」はもともと「責める」という意味ですが、チームでは変更の出どころと理由を調べるためだけに使います。よいチームは、これを経緯を理解するために使い、責任者を探すためには使いません。
